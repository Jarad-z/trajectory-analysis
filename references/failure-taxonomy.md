# 失败分类与判别规则

本分类按任务理解、信息获取、方案推导、修改执行、实现正确性和额外回归等阶段区分根因，并将验证、纠错和责任方单列。子类和过程标签参考 [LoLBench](https://arxiv.org/abs/2609.37143) 的失败模式讨论。这是用于阅读轨迹的分析框架，不是论文正式提出的分类，也不代表测量过的错误占比。

本文及 `cases.md` 的例子均为合成示例，不含真实运行案例。

## 1. 四个维度

| 维度 | 取值 | 选几个 |
|-|-|-|
| 主因阶段 | ①–⑥、G、H（模型）；X1–X4（非模型） | 单选：取起决定作用的最早阶段；①③④ 可再标一个子类 |
| 正交标签 | V1–V4（V1、V2、V4 可带子类）、过程标签、表现标签、已恢复、被掩盖 | 可多选 |
| 责任方 | 模型 / 题目 / 评测器 / 基础设施 / 混合 | 单选 |
| 置信度 | 确定 / 很可能 / 不确定 | 单选，针对引入链；对判定的贡献另写 |

“最早阶段”的意思是：如果因为没读配置（②）写错了实现（⑤），主因记 ②。相同的最终表现（例如“漏改一个文件”）可能出自不同的阶段，所以必须回到过程记录里判断。

**子类和标签怎么判。** 子类只是把父代码说得更具体，不改变主因的选择：先按判别规则（第 4 节）定代码，再看有没有合适的子类。

- 所有代码、子类和标签都由分析者读轨迹判断，不用关键词或脚本规则自动打标。`list_calls.py` 的 `-p`/`-r`/`-s` 只用来查找和展示调用，判断要回到调用和结果本身。LoLBench 用规则自动检测其中 18 个模式，这里不照搬：比如规则会把“最后一次测试之后只改了一行注释”也算成没复测，这里要看那次改动会不会影响结论。
- 每个子类都要引用支持它的调用号或可见消息。证据只够支持父代码时，只写父代码，不硬选子类；没有合适的子类时也只写父代码。
- ①③④ 的子类依据题面和当时可见的过程（读取、计划、消息）来判断，不从最终结果倒推：不能因为补丁错了，就推定 agent 误读了需求。

## 2. 主因阶段

### 模型侧

| 代码 | 类型 | 失败发生在哪里 | 虚构例子 | 改进方向 |
|-|-|-|-|-|
| ① | 任务理解错误 | 对需求、预期行为或约束的解释有误，包括有意偏离题面约束 | 要求退出账号后清除本地消息，却理解成删除服务器消息；认为原行为不合理，改成了自认为更好的行为 | 提取验收条件，核对需求与边界 |
| ② | 必要信息获取不全 | 没找到关键文件，读取范围不够，或者没有取得由框架、依赖、运行时决定的原行为 | 只看了退出登录的代码，没看到消息缓存；关键属性所在的那段输出被截断，之后没有回读 | 改进搜索、依赖追踪和读取范围；看到截断就回读 |
| ③ | 理解或修改方案错误 | 信息已经读到，却没有正确推导出依赖和影响 | 看过缓存代码，却判断退出账号不用清缓存；把原来每次请求新建的对象改成全局单例，没意识到它带有请求级状态 | 加强数据流、状态和生命周期的推理 |
| ④ | 修改执行遗漏 | 方案正确，补丁却没有落实全部必要变更 | 计划修改 A、B、C，最终只改了 A、B | 对照修改计划检查最终补丁 |
| ⑤ | 必要位置修改错误 | 位置找对了，实现逻辑有误 | 条件写反；提前返回放在有副作用的调用之后；在后台线程调用了只能在主线程调用的 API | 检查接口、执行顺序、边界条件，并运行测试 |
| ⑥ | 额外修改引入回归 | 必要修复是对的，但无关改动破坏了原有行为 | 修好了目标函数，又顺手挪动了另一个函数里的清理代码；过度编辑（over-editing） | 控制修改范围，审查额外改动，跑回归测试 |
| G | 编辑操作失败 | 修改本身没有正确落到文件里，或写入操作带来破坏性副作用 | diff 上下文不匹配，补丁没应用上；`sed -i` 的正则误伤了别处；`>` 重定向覆盖了原文件；批量脚本中途抛异常，只改了一部分；替换没匹配上，脚本仍然打印“updated” | 写入后回读核对；替换时断言命中次数 |
| H | 过程与交付失败 | 没有可以评分的交付物，原因出在执行过程上 | 超时前没有提交；把导出步骤写进了计划却没执行；陷入重复同一命令的循环；放弃 | 结束前逐项检查交付清单 |

G 和 H 分别表示编辑机制和交付过程上的失败。**H 只用于没有可评分交付的情况。** 如果有交付，“不等后台任务出结果就结束”“构建还在跑就改源码”这类问题记成过程标签（第 3 节），通常作为 V1 的成因，不当主因。

### ①、③、④ 的子类

参考 LoLBench 表 10 中需求理解、任务规划、代码编辑三个阶段的模式。

| 子类 | 判断要点 | 虚构例子 |
|-|-|-|
| ①·误读需求 | 对“要做什么”本身理解错了 | 要求退出账号后清除本地消息，理解成删除服务器消息 |
| ①·漏约束 | 目标对，但漏掉了题面写明的限制、边界或兼容要求 | 迁移做完了，但题面要求“不留任何旧框架依赖”，构建脚本里还留着 |
| ①·需求覆盖不全 | 需求有几项，agent 的目标清单（计划、TODO、最终总结）只覆盖了其中一部分 | 题面要求生产代码、测试、后台任务三处都迁移，计划里只列了前两处 |
| ①·范围判断错 | 改动边界定得过窄或过宽，包括主动缩小提交范围（见 4.3）。过宽只在 agent 明确把更大的问题当成目标时才记这一类；顺手做的额外改动造成回归，仍记 ⑥ | “全量迁移太大，先交 app 模块”；声明“顺便把数据库层也换掉” |
| ①·有意偏离 | 知道原行为，却改成了自认为更好的行为（见 4.3 表下的说明） | 注释写着 `// 改为保留 X，比原来直接丢弃更友好` |
| ③·推导错 | 信息读到了，依赖、状态或影响推错了（③ 的原有含义） | 看过缓存代码，判断退出账号不用清缓存 |
| ③·方案不可行 | 定下的方案照做完也满足不了需求 | 计划让新框架包一层、底下继续用旧框架提供对象，做完也删不掉旧依赖 |
| ④·漏落实 | 计划里有，补丁里没有（④ 的原有含义） | 计划修改 A、B、C，最终只改了 A、B |
| ④·计划半途丢掉 | 列了合理的计划，没给理由就不再照着做，剩下的步骤没做 | 5 步计划做到第 3 步就转去改别的，然后提交 |

### 非模型侧

| 代码 | 类型 | 判定信号 | 虚构例子 |
|-|-|-|-|
| X1 | 环境或基础设施失败 | 依赖下载失败、工具链不兼容、资源不足、模拟器起不来；与模型改动无关 | 判分时依赖仓库不可达 |
| X2 | 评测器或测试缺陷 | 同一个异常一次打掉多项检查，调用栈在 fixture 或测试宿主里；失败取决于题面声明不属于契约的实现选择；后续版本的 fixture 修复正好改了这一处；截图哈希相同，LLM 评委两次判定不一样 | fixture 写死了某个内部类名，换一种合法实现就全挂；用例之间共享临时目录，换个执行顺序就随机失败 |
| X3 | 题面歧义，或题面与参考行为冲突 | 题面对这个边界没有说明，按字面可以有多种合理理解；或题面与参考解、原始行为矛盾 | 题面写“兼容旧格式”，没说是只读兼容还是读写都兼容 |
| X4 | 原仓库已有缺陷 | 起点代码在同样的条件下就失败（agent 或分析者在原始 HEAD 上复现过） | 原仓库某个构建变体的测试本来就编译不过 |

- 模型引入的错误依赖或构建配置造成的环境问题，仍算模型的错（通常记 ⑤ 或 ⑥）。只有原环境本身不可用，才算 X1。
- 同版本其他 run 通过了，不能排除 X2：它们可能只是没走到出问题的那条实现路径。
- X3 经常和模型侧的主因同时成立：题面写得不够明确，但模型手上有足以判断的材料（原始代码、参考行为）却做错了。这时主因记模型侧的类，责任方记“混合”，并写明两边各自的贡献。
- 修好模型侧的根因后这一项就能通过的，不算 X3。
- 一个根因同时触发了几个检查项（比如同一个用例在两个 API 级别上各算一次分），属于评分口径问题，在“对题目的启示”里写，不单独算一个根因。

## 3. 正交标签

### 验证与纠错（V）

说明失败为什么没被发现、没被修正。可以和任何主因同时存在。

| 代码 | 含义 | 虚构例子 |
|-|-|-|
| V1 | 没有运行能覆盖这个问题的验证 | 只跑了单测，没跑集成测试；以“没有设备”为由跳过视觉检查，但环境里其实有可用的截图手段 |
| V2 | 工具输出已经暴露了问题，但被误读或被忽略 | 失败行被 `head` 截掉；`cat` 的输出第一行就是错的，没有反应 |
| V3 | 自己写的测试和实现共享同一个错误假设 | 自测断言的是自己实现的新行为，而不是外部契约 |
| V4 | 发现了失败，但没有修好或没有修完 | 看到测试失败后放弃；修改后没有重跑 |

**子类**（参考 LoLBench 表 10 中代码验证、自我修复两个阶段的模式）：

| 子类 | 判断要点 | 虚构例子 |
|-|-|-|
| V1·完全没验证 | 从引入到提交，没跑过任何构建、测试或检查 | 改完直接提交 |
| V1·最后改动后没复测 | 最后一次验证之后又改了代码，这次改动可能影响结果，之后没再验证。只改注释、日志或文档的不算 | 测试通过后又改了一处注入配置，没再跑就提交 |
| V1·写了测试没跑 | 新写或改过的测试从没被执行过，包括测试命令执行了、但过滤条件没选中它 | 新加了一个模块检查测试，测试命令只跑了另一个模块 |
| V1·跑了但覆盖不到 | 跑过验证，但覆盖不到出问题的那部分（V1 的原有含义） | 只跑了单测，没跑集成测试 |
| V2·输出被忽略 | 输出暴露了问题，却被截断盖住或没被注意（V2 的原有含义） | 失败行被 `head` 截掉 |
| V2·测试结果误读 | 把失败或无效的结果当成了通过 | 输出是 `BUILD FAILED`，却说测试全部通过；0 条测试被执行、任务是 `NO-SOURCE`，当成了通过 |
| V4·看到失败后放弃 | 发现失败，没修就结束（V4 的原有含义） | 看到测试失败，说“剩下的需要人工处理”后结束 |
| V4·修了没复验 | 验证失败后改了代码，没有再跑能覆盖它的验证就结束 | 测试失败 → 改代码 → 直接提交 |
| V4·反复无效修复 | 同一个失败反复修，每次换一种写法，失败一直在，也没有回头查原因 | 同一个“找不到依赖定义”的错误改了五次 |

V1·最后改动后没复测和 V4·修了没复验的区别：最后那次改动是针对一次失败验证的修复，记 V4；否则记 V1。

### 过程标签

不是主因，用来解释 V1 等问题的成因：不等后台任务出结果就结束、构建还在跑就改源码、用固定时长 `sleep` 轮询、多个文件合在一个命令里读导致截断、全部改完才第一次编译。

参考 LoLBench 的自我修复和工具使用阶段，再加四个：

- **原样重试**：命令失败后什么都没改，又原样执行一遍。
- **撤销自己的改动**：修复时把前面已经改对的地方改了回去。如果最终补丁因此缺了必要修改，主因记 ④。
- **工具失败未重试**：工具调用报错后没重试，也没确认结果。如果修改因此没落到文件里，主因记 G。
- **编造路径未纠正**：访问不存在的路径，报错后没去查真实路径。如果因此没拿到必要信息，主因记 ②。

### 表现标签

描述失败“看起来是什么样”，不代表原因：构建错误、运行时崩溃、行为偏差、回归、知识缺口（API 或语言特性误用）、集成错误（签名、类型、API 形式不一致）、循环、放弃、未交付、跨模块覆盖不全（参考补丁或题面涉及的文件和模块只改到了一部分；原因按 4.3 逐个文件判）。

视觉失败另分三类：状态或内容错误、结构或渲染错误、外观差异。图标换成了另一种含义或功能（返回变成关闭、可见的操作变多或变少）算内容错误；同一种含义的图标在样式、方向、颜色上不同，算外观差异。多张截图失败不等于多个独立的根因。

### 已恢复、被掩盖

- **已恢复**：中途出现、后来被 agent 自己修好的错误。问的是最终失败时不算原因；问的是这个中途错误时可以单独出卡。
- **被掩盖**：被更早的崩溃或别的失败遮住，本次没有计分的缺陷。要写“本次评分影响”（通常为 0）和“排除前面的失败后预计影响”。没有失败日志支撑时，置信度最高只能是“很可能”。

## 4. 判别规则

### 4.1 读过文件，不等于获取了必要信息

下面这些情况，在日志里都可能显示为“读过这个文件”：

- 只读了文件开头，或者关键行被截断了（读取范围没覆盖关键行）；
- 只看了某个函数，没读它调用的方法；
- 读了业务代码，没读相关的配置、资源、测试，或依赖库里的默认值；
- 读了多个相关文件，却没有把调用关系和状态传递连起来。

前三种偏向 ②，最后一种偏向 ③。文件访问记录只能证明模型接触过这些内容，不能证明它理解了。

### 4.2 没想到要改，和想到了却漏改，原因不同

以“退出账号 → 清除会话 → 清除消息缓存 → 更新首页状态”为例：模型看过缓存逻辑，判断不需要清缓存，是 ③；模型明确计划了清缓存，最终补丁却漏了，是 ④。两者在最终补丁里看起来都是“没改缓存文件”，必须结合读取记录和明确的修改计划才能区分。

### 4.3 判别表

| 要区分 | 检查什么 | 判定 |
|-|-|-|
| ② 与 ③ | 关键行是否真的进了上下文：读取范围、输出截断、压缩边界，有没有读被调用的方法、配置、资源 | 没进入 → ②；进入了但结论错 → ③ |
| ② 与 ③（框架或运行时行为） | 原行为由框架语义、依赖默认值或运行时排版决定，仓库代码里没有直接写出来 | agent 有办法取得却没去取（查依赖资源、渲染或 dump 原界面），并且没有表现出这项知识 → ②，加“知识缺口”；取得了或表现出这项知识，推理却错了 → ③ |
| ③ 与 ④ | 可见的计划、消息、TODO 或提交说明里，有没有提到要改这个位置 | 有计划但没落实 → ④；读过但没有计划 → ③（很可能）；读取和计划都没有记录 → 不确定 |
| ① 与 ③ | 模型声明的目标（计划、代码注释、最终总结）和题面验收条件是否一致 | 目标本身就偏了，包括有意偏离 → ①；目标对、推导错 → ③ |
| ①·范围判断错（主动缩小范围） | agent 有没有说过“工作量太大”“先交最小版本”“只做 X”“先留 stub/TODO”，之后有没有回来补全 | 主动缩小了提交范围、之后没有补回 → ①·范围判断错，即使已完成部分的质量很好；时间或资源上的理由不改变归类。LoLBench 对这种情况同时记 flawed plan，这里主因只选一个，记更早的 ①。“先做 X”“重点看 X”这类排序说法，如果后面继续做完了剩下的部分，不算 |
| ①·需求覆盖不全 与 ④ | 计划、TODO、最终总结里列出的需求项，有没有覆盖题面的全部要点 | 清单本身就少了 → ①·需求覆盖不全；清单完整、补丁少了 → ④ |
| 跨模块覆盖不全 | 参考补丁（没有参考补丁时按题面要求）涉及、最终补丁没改到的每个已有文件，用 `list_calls.py -p`/`-r` 查：读过没有、读到的范围、计划里有没有、是否改过又撤回 | 没读，或读取范围没覆盖关键位置 → ②；读过、没有计划 → ③（很可能）；计划过但没改 → ④·漏落实；改了又撤回 → ④，加过程标签“撤销自己的改动”。漏了多个文件时，可能分属不同主因：取起决定作用的那个作主因，其余写进卡内 |
| ⑤ 与 ⑥ | 出错的代码是否属于必要修改范围（对照题面，有参考解时也对照参考解） | 属于 → ⑤；不属于 → ⑥ |
| G 与其他 | 文件里实际落下了什么（看结果、后续读取、最终补丁或重放，不看请求） | 没落实或被破坏 → G，此时不评价方案 |
| H 与其他 | 有没有可评分的交付物 | 没有，且原因在过程上 → H；有交付 → 过程标签 |
| 模型类与 X1/X2/X4 | 失败能否在不依赖模型改动的情况下复现（no-op 基线、原始 HEAD、参考解）；修好环境或 fixture 后结果是否改变；失败是否取决于“不属于契约”的实现选择 | 是 → X1/X2/X4 |
| 与执行顺序有关的失败 | 用例的执行顺序、是否在同一进程里、前一个用例留下了什么状态或副作用 | 状态泄漏来自模型改动的测试基础设施 → 模型侧（通常是 ③）；来自原有 fixture → X2 |
| 多处差异的视觉判定 | 同一差异在别的截图或别的 run 里有没有被放过；重评时截图哈希相同，判定是否一致 | 被放过的差异记“次要”；判定不稳定的部分记 X2 噪声，并说明这对结论的影响 |

**有意的偏离也算 ①**：代码注释或消息表明模型知道原行为，却选了别的行为（例如注释写着 `// 改为保留 X，比原来直接丢弃更友好`）。这是对“保留原行为”这一约束的解释错误，不是推导错误。

**思考摘要作为证据**：判 ② 与 ③、③ 与 ④ 时，思考里的内容可以作为“信息已进入上下文”或“做过这个决定”的佐证，用摘要加 step_id 报告。只有思考支持时，置信度最高“很可能”。

## 5. 责任方与置信度

**责任方**

- 模型：主因在模型侧，非模型因素不影响结论。
- 题目：X3 单独就足以造成失败，即模型做了合理的解读却被判错。
- 评测器：X2。
- 基础设施：X1。X4 写“原仓库”。
- 混合：多个因素同时成立并各有贡献，写明各自的贡献。

**置信度（针对引入链）**

| 级别 | 条件 |
|-|-|
| 确定 | 证据链完整，每一环都有直接证据。一般是：失败日志 → 代码位置 → 写入的 step → 写入前的读取或计划记录。G 类机制错误改为：日志 → 当时的文件状态 → 写入调用 → 机制可复现，不需要计划记录 |
| 很可能 | 有一环缺少直接证据，但多条间接证据互相一致，并且已排除主要的替代解释；或者关键一环只有思考摘要支持；或者是被掩盖、没有失败日志的缺陷 |
| 不确定 | 缺少读取或计划记录，或者几种解释同样成立。只写到表现层，主因列出候选，并说明还缺什么证据 |

**对判定的贡献**单独写：决定性 / 次要 / 不确定。例如引入链确定，但同样的差异在别处被评委放过，那么贡献是“次要”。

## 6. 通过的 run 也要查

- **虚假通过或作弊**：绕过验证、硬编码预期输出、删除或弱化断言、修改测试基线、改动评测脚本。属于模型侧，在报告中单列。
- **覆盖不足**：通过只能证明 verifier 检查过的那部分。要写出哪些要求没有被测试覆盖，不要把通过说成完全正确。
- **中途错误**：用户问到时，按 SKILL.md 的“中途错误”流程处理，并说明对最终结果的影响。

## 7. 与参考补丁、定位指标比较时

公开基准的文件级定位指标比较的是模型最终补丁修改的文件集合和开发者参考补丁修改的文件集合，并不衡量模型搜索过或读过哪些文件。因此：

- 读过正确的文件但没修改，不算命中；
- 修改了参考文件但实现错了，文件级定位仍然命中，测试仍可能失败；
- 召回率低只说明最终补丁覆盖的参考文件少，不能单独证明模型没有找到这些文件；
- 漏改可能来自 ②、③，也可能来自 ④。

LoLBench 第 4.5 节同时比较了 agent 读过的和改过的文件（新增文件不计）：文件级读取召回 46.4–86.4%，修改召回 36.9–65.0%。两者之差是“读到了但没改”的部分，对应 ③ 或 ④；从没读到的部分对应 ②。分析单个 run 时也按这个思路，把漏改的文件分成“没读过”和“读过没改”两组，再按 4.3 的“跨模块覆盖不全”一行判断。

参考补丁只是一种参考实现，不一定是唯一正确的实现。与参考文件集合不同，不能自动等同于修复错误。

## 9. 证据清单

| 证据 | 可以帮助判断什么 |
|-|-|
| 题面与验收条件 | 模型是否理解了正确的目标（①） |
| 搜索结果与工具调用 | 关键位置有没有被找到（②） |
| 实际读到的代码片段、读取范围、截断标记和压缩边界 | 必要信息是否进入了上下文（② 与 ③） |
| 明确记录的修改计划、代码注释、思考摘要 | 模型是否意识到需要协调修改的位置，偏离是否有意（①、③ 与 ④） |
| 最终补丁、重放结果及其哈希 | 有没有遗漏、改错或额外改动（④、⑤、⑥、G） |
| 构建、测试和后续修正记录 | 补丁是否有效，失败是否被发现和修正（V1–V4） |
| verifier 脚本和日志、fixture 版本 diff、基线运行、截图哈希 | 失败是否来自非模型因素（X1–X4） |

这些证据都应来自可观察的过程记录。缺少记录时，结论保留为“原因不确定”。
