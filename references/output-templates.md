# 输出模板

篇幅与问题相称：终端里的简短回答只需要结论，加一两张归因卡的要点。完整报告写成本地 Markdown 文件并给出链接，文件名例如 `<题目>-<模型>-trajectory-analysis-YYYY-MM-DD.md`。由子 agent 分析时，让子 agent 以文本返回完整报告，由父 agent 落盘。

下面所有例子都是格式示意，尖括号里的内容按实际情况填写。

## 1. 步骤表（过程解读）

先写计步约定，例如：“下表的步骤按 `<文件>` 中可观察的工具调用、按发起顺序连续编号；括号里是原始 `step_id`/`seq`。决策摘要只概括工具行为和可见消息能支持的判断，标‘思考摘要’的来自 reasoning，只写高层意思，不引原文。”

| 步骤及原始编号 | 主要工具调用 | 阶段与决策摘要 | 可见 assistant 消息／思考摘要 | 返回结果与证据 |
|-|-|-|-|-|
| 12–13；seq 140–142 | `#12 Bash(command="sed -n '<起>,<止>p' <文件>")`；`#13 Bash(command="rg -n '<关键方法>' <目录> \| head -40")` | 获取原有行为和调用关系 | assistant 消息·seq 140：准备确认 `<行为>`；如有 reasoning，只放高层摘要并另标来源编号 | 输出包含 `<关键代码行>`；第二个命令被 `head -40` 截断（seq 142） |
| #13之后；seq 143 | 无工具调用 | 记录转向 | assistant 消息：`<简短可见摘录或概括>` | 这是 agent 的声明；与后续验证结果分别报告，不新增工具调用号 |

### 按阶段合并的表

用户要“第几步到第几步属于什么阶段、犯错模式是什么”时，用连续调用区间分组，末列用**问题与状态**。阶段是时间分组，不代表每个阶段都有错误。**每行仍须包含实际工具名和代表性参数**，不能因概览或篇幅限制退回“搜索、修改、验证”等行为标签。下面只是格式示意；工具名、参数、结果和状态必须换成所分析轨迹的真实记录。

| 步骤区间及原始编号 | 阶段与决策摘要 | 主要工具调用（代表性参数） | 可见 assistant 消息／思考摘要 | 返回结果与证据 | 问题与状态 |
|-|-|-|-|-|-|
| 1–3；step_id 2–4 | 信息获取：确认超时配置及调用方 | `#1 Bash(command="rg -n 'timeout' src/")`；`#3 Read(file_path="src/client.py", offset=40, limit=80)` | assistant 消息·step 2：准备调查配置；缺少思考字段时不补写 | 读取结果含 `<关键配置>`（#3）；标明是否截断 | 正常调查；不因后续出现问题就给本阶段额外算一次错误 |
| 4–8；step_id 5–9 | 修改与复验：修正配置后检查相关行为 | `#4 Edit(file_path="src/client.py", old_string="timeout=0", new_string="timeout=30")`；`#7 Bash(command="pytest -q tests/test_client.py")` | reasoning 字段摘要·step 5：计划修正超时；只概括高层意图 | 编辑成功；#7 返回 `<测试结果摘录>`，说明是否覆盖该问题 | `<问题短名>：已恢复／仍残留／验证受限／待确认，附依据` |
| #8之后；step_id 10 | 最终答复 | 无工具调用 | assistant 消息：`<已完成事项及主动披露的限制>` | 和最终测试、补丁对照；不把自报完成当成通过证明 | `<正常收尾，或延续前述同一残留问题；不新增问题计数>` |

问题名和编号先解释再使用，例如：“U1 = 超时参数未生效；U1是本报告的具体问题编号，不是错误分类代码。”同一U1在多个阶段出现，只表示引入、发现、修复、复验或残留的不同位置，不算多个独立错误。正常推进、已恢复问题、最终残留、验证受限和原因待确认分开写；分类代码在有证据的归因卡中给出。失败用例数或差分case数不直接当作独立错误数。

表前可注明：“下列调用为原记录节选，省略长路径及无关参数。”保留影响结论的命令部分（如 `--tests`、`--offline`、管道过滤和截断、后台启动及回读日志）；用调用号链接或对应原始编号支持复查。长脚本概括其关键读写和目标文件，不必复制完整脚本。

消息和思考摘要按其原始位置归入阶段，保留“assistant 消息／reasoning 字段摘要／上下文压缩摘要／分析者推断”的来源区别；消息事件不单独计工具调用。原始思考和既有推理摘要均只给简短高层概括，不导出逐字或详细内部推理；缺失/脱敏不补写。阶段概览选关键消息，完整逐步分析则保留请求范围内的消息事件。

## 2. 失败归因卡（每个根因一张）

```markdown
### 根因 N：<一句话说清错在哪>

| 字段 | 内容 |
|-|-|
| 失败表现 | 用例名或检查项；日志摘录；来源（文件:行）。有掩盖时分两栏写：本次评分影响 / 排除前面的失败后预计影响 |
| 代码位置 | 补丁 hunk 或提交源码的文件:行（没有补丁时写重放结果及哈希核对情况） |
| 首次引入 | #N（原始编号；计步来源），调用摘要；之后是否被改动过。几次写入共同造成时写：引入窗口 #A–#B |
| 引入前掌握的信息 | 已读：文件（范围、是否截断）…；没读：…；中间是否发生过上下文压缩 |
| 计划记录 | 有/无；摘录及位置（可见消息、代码注释、思考摘要分开标） |
| 主因 | 代码 + 名称，例如“③ 理解或修改方案错误”；证据够时写到子类，例如“③·方案不可行”，并附支持子类的调用号 |
| 正交标签 | V1–V4（证据够时写到子类，例如“V1·最后改动后没复测”）、过程标签、表现标签、已恢复、被掩盖 |
| 责任方 | 模型 / 题目 / 评测器 / 基础设施 / 混合（写明各自贡献） |
| 置信度 | 引入链：确定 / 很可能 / 不确定，附理由，以及考虑过的其他解释和排除理由。对判定的贡献：决定性 / 次要 / 不确定 |
| 为什么没被发现 | 跑了什么、没跑什么、输出里有没有暴露问题；agent 声称做不了的验证，环境里是不是真的做不了 |
| 改进方向 | 最少需要哪个动作就能避免或发现；可选：对题目的启示 |
```

- 置信度为“不确定”时，主因一栏写“候选：② 或 ③”，并补一行“还缺的证据：……”。
- **非模型根因（X1–X4）的卡片**：把“首次引入”改成“模型侧触发点（不是错误）”；“引入前掌握的信息”和“计划记录”只在用来说明“模型的实现是合法的”时才填。
- **中途错误的卡片**另加三栏：发现（#N 及当时的报错）、修复与验证修复（#N）、对最终结果的影响（无 / 有，影响什么）。如果错误被复制到了别处，加一栏“传播路径”。

## 3. 单 run 报告骨架

```markdown
# <题目> <模型> <run-id> 失败归因

> 计步约定：<来源文件>，共 N 个调用；原始编号写成 <seq/step_id>。thinking 的处理方式：<…>。
> 材料：<用到的原始文件>。污染声明：<事先看到过的人工结论；没有则写“无”>。

## 结论
<两三句话：失败了几项 → 归并成几个根因 → 主因和责任方 → 最关键的证据>

## 结果概览
平台状态、通过规则、分数构成（总分、各维度、是否通过）、失败的检查项；材料来源链接

## 非模型原因排查
X1–X4 逐项写：检查了什么、结论是什么

## 根因
<归因卡 1..K>

## 卡外的过程问题（已恢复，不计入失败原因）

## 关键窗口
<每个根因首次引入前后的步骤表；不默认给出全量步骤>

## 未确定的部分
<缺少的证据；哪些结论只是候选>

## 对题目的启示（可选，简短）
```

通过的 run 做中途错误分析时，“结论”一节改成：“run 通过（分数）；中途出现 N 个错误 → 归并为 K 个根因 → 对最终结果的影响”。

## 4. 多 run 报告

骨架：先写一节共同约定（材料路径缩写、run 和 trial 的对应关系、计步来源、通过规则）；然后每个 run 一节，用单 run 骨架；最后是汇总。

按 run 列出：

| run | 模型 | 分数/通过 | 根因（主因代码） | 首次引入（#N / 原始编号） | 置信度 | 对判定的贡献 |
|-|-|-|-|-|-|-|

按主因 × 模型汇总：

| 主因 | 模型 A | 模型 B | 说明 |
|-|-|-|-|

然后区分三类：

- **重复模式**：同一模型在多次 run 中犯同一类、同一位置的错；
- **偶发错误**：每次错在不同的地方；
- **同一位置的跨 run 对照**：某个 run 在同一处做对了，它当时读到了什么、写法有什么不同。

被掩盖、没有计分的潜在错误，单独列为“疑似重复”。结尾注明：这些计数只描述这一批样本，不代表普遍的错误占比。

## 5. 措辞分寸

| 证据状态 | 写法 |
|-|-|
| 证据链完整 | “#N（step_id M）写入了 `<代码>`，之后没有被改动；最终补丁第 x 行与此一致” |
| 间接证据一致 | “很可能……：日志没有直接显示 X，但 A、B、C 三条证据都指向同一个解释” |
| 缺少记录 | “原因不确定：轨迹中没有读取 X 的记录，也没有提到要修改它的计划，无法区分 ② 和 ③” |
| 只有思考支持 | “思考摘要（step_id M）显示它决定……；可见消息和动作里没有对应记录，所以只到‘很可能’” |
| agent 的自述 | “agent 声称……（seq N 的可见消息）；独立 verifier 的结果是……” |
